# Gemma 4 Developer Agent

Entry for [Google — The Gemma 4 Developer Agent](https://www.kaggle.com/competitions/gemma-4-developer-agent)
(main track, closes **2026-12-02**) and its
[Paper Track](https://www.kaggle.com/competitions/gemma-4-developer-agent-paper)
(closes **2026-11-12**). Full strategy in [PLAN.md](PLAN.md).

The submission is a `submission.zip` holding a **declarative** Google ADK agent
config — YAML, prompts, optional LoRA adapters, no Python entrypoints. The
harness (`swegemma`) runs it on SWE-bench-style tasks and scores **resolution
rate**.

## Why this is winnable

**Verified 2026-10-13** by `scripts/analyze_leaderboard.py` against a committed
leaderboard snapshot. The private set holds **58 tasks** (derived below, not
guessed), so one task is worth **0.0172**.

Top of the board is **0.24** (14/58, 2 teams) out of **3199** teams
(live 2026-10-19). We hold **0.13** (8/58) at rank **1402**, tied with **353**
other teams. The middle of the board is a pile-up: 312 teams at 7 tasks, 353 at
8, 429 at 9 — the shape of byte-identical public notebooks being copied and
resolving within one task of each other.

**Standing still costs rank.** Between 2026-10-13 and 2026-10-19 our score did
not change and we fell from rank 785 to 1402: the top stayed at 14/58 while the
population at 12–13 tasks grew about 4× (0.20: 28 → 115 teams; 0.22: 8 → 29).
Refresh the snapshot before quoting any of this — `analyze_leaderboard.py`
defaults to the newest committed one, which silently went 6 days stale once.

So the opening is narrower than this section used to claim, and sharper. The
**0.13-to-0.15 band really is noise** — one task either way, and three runs of
identical bytes have landed on 7, 8 and 9 tasks. But the **gap from us to the
top is 6 tasks (0.11)**, which is well above the 0.06 this project treats as the
evidence threshold. Somebody is genuinely resolving nearly twice what the copied
baseline does. That is a real effect, not a draw from the same distribution.

Two structural openings follow:

- **The scored budget is 60 min and 100 tool calls per task, and the field uses
  maybe a third of it.** `submit_patch` and `get_status` are free.
- **Context, not budget, is the binding constraint.** `max_model_len=32768` with
  ADK compaction at `token_threshold=14336` and `event_retention_size=5`, so a
  long single-agent trajectory forgets its own reproduction output by turn ~7.
  The budget therefore has to be spent across many short, disposable contexts,
  which is what drives the orchestrator topology.

So the whole project is built around one asset: **a cheap, low-variance local
eval on the 129 public tasks**, which nobody else has.

## Hard constraints

The local GPU is an MX550 with 2 GB VRAM and there is no Docker, so the 31B
model **cannot run here at all**.

- **Local = authoring only.** Bundles, prompts, the validator, task analysis,
  statistics, the paper.
- **Kaggle = all execution.** L4×4, `sandbox='subprocess'`, **30 GPU-h/week**,
  9–12 h session cap. ~270 GPU-h nominal over 9 weeks; planned to 200.

## How the diagnosis went wrong, and what fixed it

Runs 1 and 3 both produced **gold 74/129 (57%)**, bit-for-bit identical verdicts
on all 129 tasks. My first diagnosis — that `install_test_dependencies` being a
no-op in subprocess mode was the whole story — was **wrong**: staging the
dependencies changed nothing, because the harness-level no-op was never the
binding constraint. Run 3 captured `test_output_tail`, and with real pytest
output the 55 gold failures resolve into three distinct causes:

| Cause | Tasks | Fixable? |
|---|---|---|
| `ModuleNotFoundError: inline_snapshot` | 27 | yes — just install it |
| `ModuleNotFoundError: dirty_equals` | 7 | yes |
| Genuine test failures from **dependency version drift** | 18 | not without the grader's pinned wheels |
| Other collection / unclassified | 3 | unknown |

**The 34 missing-module failures** are the dominant cause and were trivially
self-inflicted: both packages are imported by fastapi *test* modules but
declared in neither `pyproject.toml` nor the files
`collect_from_requirements_files` scans, so dependency collection never saw
them. One collection error aborts the entire pytest invocation, so a single
absent test-only package can fail dozens of tasks. They are now installed
explicitly from a measured list in `stage_test_deps.py`.

**The 18 version-drift failures are the real, irreducible limit.** Examples:

- `rich`: `assert Syntax.guess_lexer("banana.py", "import this") == "python"`
  fails with `'ipython' == 'python'` — a newer Pygments guesses the IPython
  lexer.
- `requests`: `test_header_no_return_chars[invalid_header8/9/11]` fail on a
  newer urllib3's header validation, with 335 other tests passing.

These are not broken tasks and not broken code; they are our dependency
*versions* differing from the grader's. `/wheels` holds only 41 distinct
packages, and the full pinned cache lives in the private
`metric/gemma-4-developer-agent-metric-data` dataset. Chasing exact version
parity against a cache we cannot read is unbounded work with no verification
signal, so **we stop here and treat version drift as a known floor**.

### What this means for measurement

Resolution rate is measurable only on the subset whose tests pass cleanly in our
environment. That subset is a **paired** instrument — every config is scored on
the same tasks — so it ranks configs validly even though its absolute level will
not match the leaderboard. Its bias must be stated in any result: clean-N before
the fix was fastapi 29 + rich 42, with **requests 0 and httpx 0**, so the audit
split vanished entirely.

**Therefore gold-file localization is promoted to co-primary metric.** It needs
only the agent's patch and the gold patch — **no test execution at all** — so it
is immune to this entire class of problem, works on all 129 tasks, and sits near
p=0.45 rather than p=0.15. Resolution rate stays as the confirmatory metric on
clean-N; localization carries the iteration loop.

## First read on the noise floor

We now have three leaderboard scores for the same bundle content: **0.12**
(third party, 2026-09-23), **0.15** (third party, 2026-09-29) and **0.13**
(ours, 2026-10-01, `bundle_hash 6f3c38bf51665b01`).

All three are exactly what **7, 8 and 9 of 58** tasks display as (0.1207,
0.1379, 0.1552, truncated). Three distinct reported values landing on three
*consecutive* integers over a common denominator is the signature of ordinary
run-to-run wobble, so the observed spread is **plus or minus one task**.

**The denominator is no longer a guess (2026-10-13).** The old reading here said
"~60, and 100 also fits (12, 13, 15)". Both are now excluded: the full
leaderboard histogram pins the private set at **exactly 58 tasks**, and 100
cannot fit because it would put 0.02, 0.04, 0.07, 0.09, 0.11, 0.14, 0.16, 0.19,
0.21 and 0.23 on the grid, and all ten are unoccupied among 3199 teams. Method,
assumptions and caveats are in `src/swegemma_lab/leaderboard.py`; the one-line
version is that only 58 reproduces the 14 occupied bins as consecutive k = 1..14
with no gaps, and 0.18 being occupied while 0.19 is empty shows the display
truncates rather than rounds.

What still stands as a caveat: n = 3 for the *noise* reading, and two of the
three points are self-reported scores whose bundles were verified only by
cell-hashing the generating notebooks, not by comparing archives. **The grid fit
settles the denominator, not the variance.** A k=4 reference run would still be
the only direct measurement of the SD of identical runs; what it no longer has
to do is establish what one task is worth.

What this justifies: **the 0.13-to-0.15 band is about one task wide**, so
reading a 0.02 single-submission delta as improvement is reading noise — but
**the 6-task gap to 0.24 is not noise**, and the project's own 0.06 threshold
says so.

## Measured facts about the public task set

Computed by `scripts/analyze_tasks.py` from the shipped `tasks.jsonl`. Worth
stating explicitly because the community EDA notebooks compute their numbers at
runtime and ship no outputs, so none of this was ever actually published.

| Fact | Value |
|---|---|
| Tasks | 129 |
| Repos | fastapi 67, rich 48, requests 13, httpx 1 |
| Gold patch touches exactly 1 file | **91 (71%)** |
| Gold patch is a single hunk | 58 (45%) |
| Gold patch churn ≤ 20 lines | 81 (63%) |
| Gold churn p50 / p90 | **12 / 128 lines** |
| Gold patches that **create a new file** | **0 (0%)** |
| Gold patches touching a protected/test path | **0** |
| Gold and `test_patch` sharing any file | **0** |
| Gold patch file types | 100% `.py` |
| `hints_text` non-empty | 0 |

Three consequences:

1. **A correct patch never adds a file.** So any agent-created file in
   `/workspace` is *always* pollution — scratch-leak detection is an exact
   signal, not a heuristic, and it can be enforced as an error.
2. **Localization is the game.** 71% single-file, median 12 changed lines. This
   is why gold-file hit rate is the right low-variance surrogate metric.
3. **`rich`'s problem statements have a median of 146 chars against fastapi's
   677.** The confirm split carries far less information per task, so prompt
   rules of the "extract every identifier from the issue" kind degrade badly
   there. Any change that helps fastapi must be checked on rich before shipping.

The largest gold patch (`rich_3930`: 12,714 lines across 26 files) is almost
certainly unresolvable and is a candidate for exclusion once gold calibration
runs.

## Verified harness facts

Read from `reference/HARNESS_README.md` (the authoritative 49 KB spec shipped
with the competition data). This section is the project's source of truth; when
it and the spec disagree, the entry says so.

- Patch extraction is `git add -N . && git diff --binary HEAD`, so **anything
  left in `/workspace` ships inside the patch**.
- `write_file` resolves under `/workspace` and **rejects `/tmp`**; scratch needs
  a `run_command` heredoc.
- Test files plus `conftest.py`, `pytest.ini`, `pyproject.toml`, `setup.cfg`,
  `tox.ini` are **force-reset to baseline** before the hidden `test_patch`.
  Editing them can never help.
- The harness **auto-extracts the working tree even without `submit_patch`**, so
  reverting a plausible fix guarantees a zero. Never revert.
- Three consecutive turns with no tool call end the session.
- `read_file` caps at 150 lines / 10,000 chars; `run_command` output truncates at
  5,000 chars. So `read_file` is strictly better than `sed -n` for reading.
- No ripgrep, no `tree`, offline. Use `git grep -n`.
- `search_similar_code` **does not embed free text** — it resolves the query
  against stored node keys and returns full node source. Reports of >100k chars
  against a 32k window make one bad call capable of destroying a trajectory.
- Graph tools know synchronous CALLS edges only and **miss async functions**,
  which is most of fastapi and httpx.

### Read from the harness source (W1 recon, 0 GPU-hours)

`notebooks/00_harness_recon.ipynb` captured all 642 harness source files to
`reference/harness_facts/`. Facts below cite `file:line` in that archive.

- **`..` in paths follows a split rule, and `HARNESS_README` gets it wrong.**
  `!include` resolves via `validate_sandboxed_path`, which permits `..` as long
  as the target stays inside the bundle root (`yaml_loader.py:70`). But
  `config_path` on `sub_agents`/`agent_tool` and every `skills:` entry go through
  `ensure_no_traversal_components`, which rejects `..` **lexically and
  outright** (`context.py:106`, `discovery.py:640`, `schema.py:321`). So
  `!include ../prompts/analyzer.md` is legal — which is why the 0.15 bundle
  works — while `config_path: ../x.yaml` is a `PathTraversalError` and a 0.00.
- **`agent.yml` is never discovered.** `_ROOT_CONFIG_NAMES = ["agent.yaml",
  "root_agent.yaml"]` (`discovery.py:24`). `HARNESS_README` §2.2 also lists the
  `.yml` spellings; the loader never looks for them, so shipping `agent.yml`
  raises `MissingRootConfigError` and scores 0.00. The validator rejects it.
- **Sub-agent tool calls consume the root agent's budget.** There is one
  `SwegemmaContext` per task, and `check_budget` increments a single
  `tool_calls_used` under one lock (`context.py:467`), so every agent in the tree
  draws on the same 100 calls. Deep topologies are not free.
- **Exhausting the budget does not end the session**; it makes each gated tool
  return a `BudgetExceeded` error JSON. `submit_patch` and `get_status` pass
  `count_tool_call=False` and so skip every check, staying usable afterwards
  (`tools/base.py:60`).
- **Library budget defaults are `time_minutes=60.0`, `tool_calls=None`,
  `turns=None`** (`budget.py:14`) — i.e. unlimited calls and turns unless set.
  **`EvalConfig.__post_init__` does no clamping at all** (`config.py:118`): it is
  plain "if not None" precedence with no `min()` and no ceiling. So the 60/100
  figures come from the private `scripts/inference.py`, which is not shipped in
  the wheelhouse. **Whether `eval_config.yaml` can raise them is therefore still
  open** — the library would allow it; the scoring script may not.
- **`hints_text` is injected** into the prompt and into `session_state['hints']`,
  but only when non-empty (`agent_runner.py:109,395`). It is empty in all 129
  public tasks, so a prompt containing a bare `{hints}` is a guaranteed
  `KeyError`; it must be written `{hints?}`. The validator enforces this.
- **`skills/` is genuinely loaded**, via ADK's `SkillToolset`
  (`compiler.py:23`).
- **`seed` is an accepted generation field** (`schema.py:221`,
  `limits.py:237`), so it passes validation. Whether it reaches vLLM through
  LiteLLM is still unverified, and vLLM is not bitwise deterministic under
  continuous batching anyway.
- **`!include` accepts only `.md`, `.txt`, `.yaml`, `.yml`**, max nesting depth
  10 (`yaml_loader.py:23-29`).

## Open items

Settled in W1 recon: sub-agent budget sharing, `skills/` loading, `hints_text`
injection, `..` semantics, root config names, `seed` acceptance. Still open:

1. **Whether `eval_config.yaml` can *raise* 60 min / 100 calls.** The library
   does no clamping, but the ceiling is applied in the private
   `scripts/inference.py`, which the wheelhouse does not ship. Probe it instead:
   submit a bundle declaring `max_tool_calls: 200` and read the realised call
   counts out of the traces.
2. Whether `run_command` wall time counts against the 60-minute budget. If yes,
   the verify-repair loop costs 3× what it looks like. Measurable from traces.
3. Whether declarative YAML supports a `LoopAgent` early exit / escalate.
   `max_loop_iterations` is capped at 500 (`config.py:34`); the exit path is not
   yet confirmed, so assume `max_iterations` is the only bound.
4. Whether `seed` actually reaches vLLM through LiteLLM. It validates, but vLLM
   is not bitwise deterministic under continuous batching, so **build nothing on
   determinism** either way.
5. Whether paper-track eligibility requires a main-track submission. Assumed it
   might, which is why `v00` shipped first.
6. Whether `kernel-metadata.json` can request L4×4 or whether that needs one

## Layout

```
bundles/          authored variants; _shared/ holds common prompts and configs
  v00_public_baseline/   faithful reproduction of the 0.13-0.15 public bundle
src/swegemma_lab/ validate.py (offline validator), build.py, tasks.py, stats.py
scripts/          CLI entry points
notebooks/        Kaggle notebooks; only these touch a GPU
kernels/          kernel-metadata.json per notebook, for `kaggle kernels push`
data/tasks/       tasks.jsonl and the repo-split id lists
reference/        HARNESS_README.md, the official starter, sample_submission
ledger/           run results, synced from the Kaggle runs dataset
dist/             build output (gitignored; reproducible from bundles/)
paper/            paper-track manuscript
```

Variants are **directories, not branches**, because they have to be diffed and
run side by side. `build.py` copies `_shared` then the variant's overrides into
`dist/<variant>/`, so the directory that gets validated is the one that gets
zipped — one code path, no drift.

`bundle_hash` is sha256 over sorted `(posix relpath, LF-normalized bytes)`. It
makes byte-identity provable, lets repeated runs of one config pool in the
ledger, and lets us reproduce the community's "identical archive, different
score" observation deliberately.

## Commands

```powershell
python -m pytest                                             # 171 tests, ~5s, no GPU
python scripts\analyze_tasks.py                              # task set shape + split lists
python scripts\build_bundle.py --variant v01_hygiene --zip
python scripts\submit.py --variant v01_hygiene --note "clean-N 0.21 (k=2)"
python scripts\push_dataset.py -m "v01 hygiene"              # publish lab code + bundles
kaggle kernels push -p kernels\00_harness_recon

python scripts\report.py                                     # ledger inventory + panels
python scripts\report.py --arm v01_hygiene --baseline v00_public_baseline

python -X utf8 scripts\analyze_traces.py --traces <dir>      # per-call behaviour
python -X utf8 scripts\analyze_traces.py --traces <dir> --task fastapi_11355
python -X utf8 scripts\analyze_traces.py --traces <A> --compare <B> ^
    --label-a v00 --label-b v03                              # paired arm comparison
```

`--compare` pairs two arms **within task** and reports `coder_call_share`,
`reissue_rate`, `counted_calls` and `workspace_writes` as mean differences with
standard errors (`stats.paired_delta`). All four denominate on **calls that spent
budget**, not calls emitted: `analyze_traces.reconcile` splits emitted calls into
counted / free / agent_tool / malformed / refused, and only `counted` moves the
harness's `tool_calls_used`. The metric was `n_calls` over emitted calls until
2026-10-12, which let post-exhaustion spinning dominate it — fastapi_13713 scored
`reissue_rate` 0.837 on 565 emitted calls, of which 310 were refused and 146 were
free `submit_patch` calls made after its budget was already gone. Pairing is the design, not a refinement: one
probe_c12 task used 173 tool calls against a median of 31, so an unpaired estimate
would spend all of its power on between-task variance.

**Resolution rate is deliberately absent from `--compare`.** Twelve tasks at k=1
cannot separate a +0.05 effect from noise, so reporting it there would invite
reading noise as a result. It belongs in `report.py`, against the k=4 reference.

Beware the aggregate. Pooling calls across tasks weights each task by how many
calls it made, which is backwards when the pathology under study *is* making too
many calls: probe_c12's coder share is **47% aggregate but 28.9% per task**, the
gap created by two outliers. Quote the per-task figure.

`analyze_traces.py` answers a question the ledger cannot: the ledger says a task
spent 29 calls and produced nothing, and only the trace says whether it looped on
one failing edit, read files forever, or thrashed between hypotheses — three
problems with three different fixes. It reads the structured `tool_calls` field
on each agent step, reports calls **per author** (sub-agent calls spend the root
agent's budget, so who spent them is the question) and counts **verbatim
re-issues** of a byte-identical call, which is the signature of a stuck loop.
This is what revealed that `code_analyzer` was consuming 53% of the call budget.

Use `-X utf8`, not `PYTHONUTF8=1`: traces carry emoji from repository issue text,
cp1252 dies on them, and `-I` implies `-E`, which discards the env var.

`report.py` reads only rows already on disk, so it costs no GPU and launches
nothing. It reports **three** metrics side by side, not one: `resolved` (the
competition metric, and the noisiest readout available), `gold_hit` (the agent's
patch touched a file the gold patch touched) and `gold_exact`. Localization sits
near p=0.45 rather than p=0.15 and needs no test execution, so it detects a
change 2 to 3 times smaller for the same quota.

Read them together. Localization up with resolution flat means the agent is
finding the right file and fixing it wrongly — a different problem from
localization flat with resolution down. **The ship rule still keys on
resolution**: a surrogate is a diagnosis and a triage instrument, never the
thing being optimized, because optimizing a surrogate is how you win the
surrogate.

The gold-overlap flags are stored on each ledger row rather than recomputed,
because the patches live in the swegemma results directory, which does not
reliably survive the trip back from a Kaggle session, while the ledger always
does.

`build_bundle.py` and `submit.py` both exit non-zero on any validator error, so
they are safe to gate a submission on. Submissions are limited to **one per
day** and 2 final submissions count, so a bundle that fails to load costs a
whole day.

## Operational notes

Things that cost time to discover. Encoded in the tooling, recorded here anyway.

- **The submitted file must be named exactly `submission.zip`.** Any other name
  returns a bare `400 Bad Request` with no explanation. `scripts/submit.py`
  enforces it; do not use `kaggle competitions submit` by hand.
- **Always put `bundle_hash` in the submission message.** Without it a
  leaderboard score cannot be matched back to the bytes that produced it, and
  the local-to-LB calibration map becomes guesswork.
- **The official starter's wheelhouse path only works in the scoring
  environment.** `/kaggle/input/datasets/metric/...` silently yields "installing
  0 wheels" in a normal notebook. Attach the public dataset
  `metric/gemma-4-developer-agent-wheelhouse` (867 MB) and locate it by name;
  `notebooks/00_harness_recon.ipynb` shows the discovery pattern.
- Kaggle **extracts** zip-mode dataset uploads on ingest, so `push_dataset.py`
  can use `-r zip` for a fast single-shot upload and notebooks still see real
  paths like `/kaggle/input/swegemma-lab/scripts/inspect_harness.py`.
- Publish the dataset **before** pushing a kernel that attaches it; a kernel
  that starts while the dataset is still processing sees an empty mount.
- `enable_gpu: true` in `kernel-metadata.json` requests "a GPU", not L4×4
  specifically. Expect to set the accelerator once in the browser per kernel;
  the setting persists across later CLI pushes. (Open item 9.)

## Rules we hold ourselves to

**Statistics.** Never decide from a single run. The dominant variance is the
agent's own stochasticity, not task sampling — identical archives have scored
0.03 apart. `stats.py` implements paired k-sample proportions
(SE ≈ 0.030/√k), the ship rule, and Beta-Binomial sequential stopping. McNemar
is reported as a secondary statistic only; on k=1 runs it treats sampling noise
as a treatment effect, and `tests/test_stats.py` demonstrates that empirically.
**A leaderboard delta below 0.06 never changes a decision.**

**Generalization.** Tune on fastapi+httpx (68), confirm on rich (48), audit on
requests (13) sparingly and late. The public set is 90% fastapi+rich but the
private set is believed to hold different repos, and the one competitor who
wrote repo-specific prompt rules scored **0.05 — below the naive baseline**. The
validator errors on any library name in a shipped prompt, overridable only with
an explicit `# generic-ok: <reason>`.

**No gold-patch laundering.** We hold all 129 gold patches. Their only
sanctioned use is offline localization scoring. Prompt text may be derived from
failure traces, never from gold patches — reading sixty gold patches and
distilling them into instructions is overfitting with extra steps.
